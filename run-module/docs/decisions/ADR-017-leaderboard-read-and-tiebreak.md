# ADR-017: Leaderboard Read and Tie-break Design

## Status
Accepted

## Context
The \/v1/leaderboard\ endpoint must return ranked players across three defined windows (daily, weekly, alltime) matching the logic in RM-6.1. Importantly, the specification requires ties to be broken by the *earliest achievement* timestamp (the user's oldest \capture_events.occurred_at\). 
Additionally, pagination must be robust against score updates between pages, negative scores must be accurately reflected rather than clamped, and unsupported scopes (\city\, \riends\) must be handled as unresolved product decisions.

## Decisions

### 1. Tie-Breaking by Timestamp
**Decision**: When rendering a page of the leaderboard, we fetch exactly the requested limit of items from Redis using our cursor strategy (see below). Then, we group these fetched items by score. For any group with $\ge 2$ members, we query PostgreSQL for their earliest \capture_events.occurred_at\ using a single \SELECT MIN(occurred_at) ... WHERE actor_id = ANY()\ query. We sort the members within that score group by their timestamps (ascending, nulls last) and assign them their absolute 1-based ranks sequentially.
**Rationale**: We deliberately DO NOT encode the timestamp into the fractional component of the Redis score. Leaderboard scores represent real signed geographic areas (square metres) up to billions of units; using float64 mantissas to encode timestamps would cause precision loss and corrupt the scores. Reading from Redis first and resolving ties only for the retrieved adjacent equal scores ensures the primary path remains (\log n)$ while flawlessly satisfying the specification for rare ties.

### 2. Cursor Pagination Design
**Decision**: The \cursor\ encodes the \score\ and \member\ of the last entry in the returned page prior to timestamp sorting. To fetch the next page, we use a pipelined approach to fetch strictly remaining members of the same score (using Redis standard lexicographical ordering), and then fetch strictly lower scores using \ZREVRANGEBYSCORE key (score -inf\. 
**Rationale**: The specification mandates an exclusive bound rather than a global offset (\LIMIT offset\), as offset-based pagination skips or duplicates rows when scores change between requests. By encoding the score and member, we flawlessly paginate through ties without dropping users or duplicating data.

### 3. Negative Scores
**Decision**: Negative scores generated by expiries or carves are preserved and surfaced directly in the API response. They are NOT clamped to zero. 
**Rationale**: A user whose net week is negative is genuinely mathematically ranking below someone sitting at zero. Hiding this by clamping to zero would distort relative ranks and make the leaderboard incoherent.

### 4. Unsupported Scopes 
**Decision**: The endpoint accepts \scope=global\ only. Requests for \scope=city\ or \scope=friends\ immediately return a 400 Bad Request.
**Rationale**: As defined in ADR-015, city and friend scopes are unresolved product decisions. The database lacks any city/region assignments or a friend graph. Rejecting these scopes with 400 correctly signals the missing product definitions rather than silently treating them as valid but empty.

### 5. Weekly Window Computation
**Decision**: The \weekly\ window is computed on-the-fly via \ZUNIONSTORE\ across the last 7 \lb:day:*\ keys into a temporary key (\lb:weekly:<date>:tmp\). This temporary key is given a short TTL of 60 seconds.
**Rationale**: This prevents rebuilding the weekly aggregate on every single request, protecting Redis under heavy read load while ensuring the weekly leaderboard is never more than a minute stale.
