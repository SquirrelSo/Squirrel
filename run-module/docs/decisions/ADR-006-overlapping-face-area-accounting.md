# ADR-006: Overlapping Face Area Accounting and Union Fix

| Field          | Value                                             |
|---------------|---------------------------------------------------|
| **Status**     | Accepted                                          |
| **Date**       | 2026-09-19                                        |
| **Ticket**     | RM-3.2b                                           |
| **Authors**    | Run Module team                                   |
| **Supersedes** | ADR-005 (Partially - ST_MakeValid decision)       |

---

## Context

In RM-3.2a, we observed a 1.19% mismatch between the `area_m2` emitted by the pipeline and the area of the geometry stored in PostgreSQL after applying `ST_MakeValid` during the `INSERT_TERRITORY` operation for the noisy figure-eight fixture. 
ADR-005 originally concluded that `ST_MakeValid` was erroneously shrinking valid geometries, and removed `ST_MakeValid` in favor of storing OGC-invalid geometries directly from the pipeline.

However, subsequent analysis revealed that the pipeline's output (`polyResult.multiPolygonWkt4326`) was an assembly of un-unioned polygon faces generated by `ST_Polygonize`. Adjacent faces in a figure-eight share edges. While their area does not directly overlap in a planar graph, when serialized as a single `MULTIPOLYGON` boundary, they form self-intersecting boundaries that violate OGC simple feature specifications. 

The core issue was that the `area_m2` was computed correctly in the pipeline using a projected `ST_Union` of the faces, but the pipeline returned the un-unioned text-concatenated faces back to the caller instead of the unioned geometry. 

## Decisions

### 1. Return Unioned Geometry from the Pipeline
The pipeline now calculates `ST_Union` over the full collection of faces in projected (AEQD) coordinates. After validation, we use a custom `unprojectAeqdTo4326` function to unproject the unioned geometry back into EPSG:4326 coordinates, and return that as the final `multiPolygonWkt4326` output. 
This guarantees the pipeline outputs exactly the same geometry that was used to compute the area and perimeter, meaning the area matches perfectly.

### 2. Assert Union Validity
If the resulting `ST_Union` yields an invalid geometry and forces `validateGeometry` to run a repair, the pipeline will now reject the geometry with `invalid_geometry` rather than returning a repaired shape that alters area.

### 3. Restore ST_Multi in Database Writes
Because the geometry output is now a single properly unioned shape (often resolving to a valid `POLYGON` instead of a `MULTIPOLYGON`), we have restored `ST_Multi(ST_GeomFromText($4, 4326))` to `INSERT_TERRITORY` to ensure the stored column type is respected. We strictly do **not** use `ST_MakeValid` on insert, as the geometry is already valid from the pipeline, and we rely on the consistency guard to catch any shape deviations.

## Consequences

- The pipeline now correctly emits a single OGC-valid geometry (a single `POLYGON` or a proper `MULTIPOLYGON` with holes, instead of overlapping un-unioned faces).
- The geometry stored in `territories.geom` is `ST_IsValid = true`.
- The `CHECK_TERRITORY_AREA` consistency guard now passes without triggering any rollbacks on standard fixtures.
- This fully enables downstream operations in RM-5.1 (`ST_Difference`), RM-5.2 (sliver measurements), and RM-3.3 (`ST_AsMVT`), which require OGC-valid geometry to behave predictably.
- The WKT golden files have been regenerated, reflecting the true unioned structures.
